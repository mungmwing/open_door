# 실시간 카드 전투 구현

최신 몬스터·유물·소환·관전 기능 및 SQL 적용 순서는 [전투 확장/최종 QA 문서](combat-expansion.md)를 따릅니다. 아래 내용은 단계별 구현 기록입니다.

## 가능 여부

기존 Svelte 5 / Vite / Supabase Auth와 `profiles.role`, `characters.owner_id`, `character_cards`를 재사용한다. 별도 서버 배포 없이 PostgreSQL RPC가 전투를 판정하고 Supabase Realtime이 변경을 전달한다. 운영 데이터베이스에는 쿼리를 실행하지 않는다.

## 전투 규칙

- 관리자만 방을 생성하고 본인 방을 설정·시작·종료한다. 1~6명이 자신의 캐릭터로 참가한다.
- 참가 시 서버가 보유 카드 수량, HP, 초상화를 복사한다. 원본 캐릭터의 HP나 카드 수량은 전투로 변경하지 않는다. 덱은 1~100장, 시작 HP는 현재 HP를 사용하며 HP가 0이면 참가할 수 없다.
- 기존 카드 설명은 자유 형식이라 임의 해석하지 않는다. 관리자는 캐릭터 관리의 카드 탭에서 전투 효과를 미리 저장할 수 있다. 참가 시 사전 설정이 방에 복사되며, 미설정 카드만 방에서 추가 설정한다. 방에서 변경한 규칙은 그 방에만 저장한다. 모든 카드 설정을 완료해야 시작한다.
- 매 턴 기본 에너지 3, 카드 5장 드로우, 손패 상한 10장. 부족한 뽑기 더미는 버림 더미만 섞어 보충한다. 선천 카드를 첫 손패에 우선 배치하며, 선천이 5장보다 많으면 최대 10장까지 첫 손패를 늘린다.
- 사용한 카드는 버림 더미로 이동한다. 사용 후 소멸 설정은 소멸 더미로 이동한다. 파워 카드는 별도 파워 영역으로 이동하며 소멸 시 발동 효과를 실행하지 않는다. 파워에 사용 후 소멸을 명시한 경우에는 소멸을 우선한다. 에테리얼은 턴 종료 시 소멸하고, 나머지 유지 카드는 남는다.
- 사용 효과 다음에 `card_drop_count`만큼 자신이 추가 드로우한다. 사용 효과에 등록한 드로우와 합산하며 손패 상한은 10장이다. 사용 중인 카드를 다시 뽑지 않도록 더미 이동 전에 처리한다. 에테리얼로 소멸만 할 때는 추가 드로우를 실행하지 않는다. 카드의 기본 효과와 실제 소멸 시 발동 효과를 각각 설정할 수 있다. 피해, 방어도, 회복, 드로우, 에너지, 힘, 약화, 취약, 중독을 지원한다. 대상은 자신/선택 적/전체 적/무작위 적/선택 아군/전체 아군이다.
- 힘은 공격 피해에 더한다. 약화는 공격 25% 감소, 취약은 받는 공격 50% 증가(내림). 방어도는 공격을 먼저 흡수한다. 중독은 자기 진영 턴 시작 시 방어를 무시하는 피해를 주고 1 감소한다. 약화/취약은 자기 진영 턴 종료에 1 감소한다.
- 플레이어는 자기 카드만 사용하고 자기 턴만 종료한다. 살아 있는 전원이 종료하면 서버가 적의 공격/방어/강타 순환 행동을 실행한다. 적 공격은 살아 있는 플레이어 사이에서 순환하여 대상을 정하고 화면에 예고한다.
- 적 전멸 시 승리, 플레이어 전멸 시 패배. 방장은 중도 종료하거나 연결이 끊긴 참가자의 턴을 대신 종료할 수 있다.
- 참가 후 새로고침해도 URL의 방 ID로 복귀한다. 대기 중 나가기는 덱을 제거하고 재참가 시 최신 덱을 복사한다. 전투 중에는 화면을 나가도 참가 상태를 유지한다.

## 데이터·권한

`combat_rooms` 한 행에 방 설정, 버전, 참가자 목록과 전투 스냅샷을 저장한다. 방장/참가자만 상세를 읽는다. 인증된 사용자는 요약 목록 RPC로 방을 찾는다. 직접 INSERT/UPDATE/DELETE는 허용하지 않고 RPC에서 인증, 방장/소유권, 단계, 카드/대상/에너지와 버전을 확인한다. 행 잠금으로 동시 변경을 직렬화하며 오래된 버전의 요청은 거부한다. 협동 방의 참가자에게는 파티의 덱과 손패가 공개된다.

## SQL 적용

`supabase/queries/create_realtime_combat.sql` 전체를 Supabase SQL Editor에서 직접 실행한다. 앱은 SQL을 자동 적용하지 않는다. 기존 카드/인벤토리 테이블은 수정하지 않는다. 기존 `public.is_admin()` 함수와 기본 TRPG 테이블이 필요하다. 선택 카드 필드는 `to_jsonb`로 읽으므로 과거 스키마에서도 기본값을 사용한다.

카드 사전 설정 기능은 위 기본 전투 SQL 적용 후 `supabase/queries/add_card_combat_presets.sql` 전체를 추가로 실행한다. 기본 전투 SQL을 이미 적용했다면 새 파일만 실행하면 된다. 이 추가 쿼리는 `character_cards.combat_rule`과 누락된 카드 편집 컬럼, 사전 설정 검증/복사 트리거 및 원자적 저장 RPC를 만든다. 기존 카드 데이터는 일괄 수정하지 않는다.

Realtime은 방 테이블만 publication에 추가한다. 실시간 연결이 끊겨도 3초마다 서버 상태를 확인하며 재연결 시 다시 조회한다. SQL 미적용 시 페이지에서 설정 안내를 보여 준다.

참고: [Supabase DB 함수](https://supabase.com/docs/guides/database/functions), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Realtime](https://supabase.com/docs/guides/realtime/postgres-changes).

## QA 결과

### 로컬 검증 완료

- `npm run build`: 성공. 새 전투 페이지는 별도 청크로 로드한다. 기존 편집기 관련 500KB 초과 청크 경고는 남아 있다.
- `node scripts/combat-qa.mjs`: **39개 검증 통과**. 인메모리 PostgreSQL(PGlite)에 제공 SQL 전체를 적용 및 재적용하고 실제 `authenticated`/`anon` 역할로 RPC와 RLS를 실행했다. 운영 DB 연결·스키마 변경·데이터 변경은 없다.
- 권한: 비로그인 RPC, 일반 사용자의 방 생성/설정, 비참가자 상세 열람, 직접 UPDATE, 내부 함수 호출, 남의 손패 사용을 차단한다.
- 요청 검증: 이전 버전, 중복 참가/카드 사용, 잘못된 대상/규칙/수치, 에너지 부족, 준비 미완료/미설정 카드 시작, 종료 후 행동을 차단한다. 실패 요청이 상태/버전을 변경하지 않는 것을 확인했다.
- 전투: 실제 카드 수량 복사, 선천, 유지/에테리얼 우선순위, 파워/소멸 효과, 드로우 상한, 덱 보존, 에너지 재충전, 방어/힘/약화/취약, 중독, 회복 상한, 적 공격/방어, 승리/패배 저장, 강제 턴 종료, 대기실 재참가를 확인했다.
- 브라우저: 원래 앱의 `#combat` 메뉴와 로그인 진입을 확인했다. 별도 로컬 QA 서버에서 동일한 Svelte 페이지와 SQL을 사용해 방 생성 → 두 플레이어의 보유 덱 참가 → 적 편성 → 카드 규칙 저장 → 전원 준비 → 전투 시작 → 대상 지정 카드 사용 → 새로고침 복귀 → 전원 턴 종료 → 적 자동 공격 → 다음 턴 → 승리를 실행했다.
- 실시간 장애 대체: QA 서버는 실시간 채널 실패를 의도적으로 반환한다. 3초 조회로 다른 사용자의 참가/준비/피해/결과가 반영되며, 실제 충돌 안내와 재시도가 동작한다.
- 화면: 데스크톱과 390px 모바일에서 전장/손패를 확인했다. 모바일 입력·버튼의 가로 넘침이 없고, 선택한 카드의 대상과 사용 버튼을 화면 아래에서 조작할 수 있다.
- QA 수정: 기존 패널의 배경 필터가 하단 고정 버튼을 화면 밖으로 밀어내는 문제를 전투 페이지에서 해결했다. 플레이어 턴 종료 때 만료될 취약을 적 피해 예고에 잘못 포함하던 계산도 수정했다.

### 운영 환경에서 남은 적용·확인

- [ ] 사용자가 `supabase/queries/create_realtime_combat.sql` 전체를 SQL Editor에서 적용
- [ ] 실제 관리자·플레이어 계정 2개 이상으로 Realtime WebSocket 구독 및 재접속 확인

이 두 항목은 운영 DB 변경을 직접 실행하지 말라는 요청을 지켜 수행하지 않았다. 로컬 QA는 PostgreSQL 로직과 화면 흐름을 검증하며, Supabase의 실제 publication/WebSocket 서비스 동작까지 대체하지 않는다.

### 재현 방법

1. `npm install --prefix output/combat-qa --no-audit --no-fund @electric-sql/pglite`
2. `node scripts/combat-qa.mjs`로 SQL/권한/전투 검증.
3. 선택적으로 `node scripts/combat-qa-server.mjs`를 실행하고 출력되는 로컬 주소에서 UI를 검증한다. `?user=admin`, `?user=alice`, `?user=bob`는 이 임시 서버에만 존재하는 테스트 계정 선택이다. 실제 앱에는 테스트 인증 경로나 가짜 데이터가 포함되지 않는다.

## 이용 순서

1. SQL 적용 후 상단 **전투** 메뉴를 연다 (`#combat`). 관리자 메뉴와 미니게임에서도 접근할 수 있다.
2. 관리자는 방을 만들고 적 편성을 저장한 뒤 초대 주소를 공유한다.
3. 플레이어는 로그인 후 자신의 캐릭터로 참가한다.
4. 카드 설정에 저장된 효과는 자동으로 불러온다. 미설정 카드는 방장이 원문을 보고 사용 효과/소멸 효과를 저장한다. 추가 드로우 개수는 자동 적용된다. 설명에만 있는 드로우나 장비 보너스는 명시적으로 설정한다.
5. 플레이어가 모두 준비 완료하면 방장이 전투를 시작한다.
6. 플레이어는 손패 → 대상 → 카드 사용 순서로 행동하고 턴을 종료한다. 전원이 종료하면 자동으로 적이 행동한다.

### 카드 사전 설정 사용법

1. 관리자 → 플레이어 선택 → **카드** 탭 → 원하는 카드 선택.
2. 기본정보 바로 아래의 통합 편집기에서 키워드와 효과를 설정한다. 효과를 추가/변경하면 설정됨 상태가 되며, 효과가 없는 카드는 **현재 효과 설정 완료**를 누른다.
3. 사용 효과/소멸 시 발동 효과를 추가하고 종류·수치·대상을 설정한다. 각 항목 옆 **?**를 누르면 설명이 펼쳐진다. 추가 드로우는 사용 효과 안에서 설정한다. 대표 대상은 실제 사용 효과에서 자동 반영한다. 드로우와 에너지는 아군만 선택할 수 있고, 소멸 효과는 클릭 대상이 필요 없는 자신/전체/무작위 대상으로 제한된다.
4. **전체 변경사항 저장**을 누른다. SQL 미적용 안내가 나오면 추가 SQL 적용 후 다시 저장한다.
5. 플레이어가 새 방에 참가하면 설정을 자동으로 사용한다. 이미 참가한 대기실은 나갔다가 재참가하면 최신 설정을 불러온다.

방에서의 설정 변경은 원본에 역으로 저장하지 않는다. 원문 효과 설명과 전투 수치는 별도 항목이므로 자동 전투는 구조화된 수치를 기준으로 판정한다. **사용·소멸 효과 설정 해제** 후 저장하면 이후 참가하는 방에서 다시 설정해야 한다.

### 이번 SQL 적용

이미 기본 전투 SQL을 적용했다면 **supabase/queries/fix_combat_card_keywords.sql** 전체를 수동 실행한다. 이 파일은 방 액션 함수를 교체하며 데이터 일괄 수정은 하지 않는다. 카드 사전 설정 SQL을 아직 적용하지 않았다면 **add_card_combat_presets.sql**도 적용한다. 처음 설치할 때는 최신 **create_realtime_combat.sql → add_card_combat_presets.sql** 순서로 실행하면 키워드 수정도 포함된다.

수정 함수는 적용 이후의 전투 행동에 사용된다. 기존에 소멸된 파워 카드를 다른 더미로 옮기는 데이터 보정은 하지 않으므로 수정 규칙은 새 방에서 확인한다. 이미 참가한 대기실에서 카드 설정을 다시 불러오려면 나갔다가 재참가한다.
